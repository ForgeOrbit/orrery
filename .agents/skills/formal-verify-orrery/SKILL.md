# Formal Verify Orrery

Exhaustive finite-state model checking for Orrery's highest-stakes concurrency, lifecycle, and access-boundary invariants. The checker extracts the active locks and transition guards directly from Orrery's server source and SQL migrations, then runs a breadth-first search (BFS) over all reachable concurrent interleavings to verify safety and liveness properties.

## Run the Check

One command, zero external dependencies (requires only Python 3.10+, runs in `< 0.3s`):

```bash
python3 .agents/skills/formal-verify-orrery/scripts/verify.py
```

For machine-readable output (extracted code facts + counterexample traces):

```bash
python3 .agents/skills/formal-verify-orrery/scripts/verify.py --json
```

Exit code `0` means every property passed; exit code `1` means at least one property failed and its shortest counterexample trace was printed in Orrery's own function names.

## Tool Choice

We use a **zero-dependency Python 3 exhaustive BFS model checker** paired with source-guard extraction rather than TLA+/TLC or Quint because:
1. Neither a JVM/TLC nor Quint is installed on the dev environment or CI by default, while `python3` is always available.
2. Source-guard extraction binds the model directly to the live TypeScript and SQL files, so removing a lock or guard (e.g., dropping `.for("update")` or `lockWorkspaceForMutation`) immediately switches the model to the unguarded transition relation and produces the real counterexample trace.
3. If you author a new TLA+ specification for a future subsystem (e.g., #27 project permissions or #38 account deactivation), read its output with `/statechart`.

## What Is Not Covered

- **SQL/Drizzle runtime semantics & deadlocks across unrelated tables**: The model checks the extracted design and lock ordering, not PostgreSQL's query planner or migration SQL syntax. Always pair this skill with `pnpm test` (real Postgres via Testcontainers) and `/verify-orrery` for end-to-end runtime proof.
- **UI & HTTP transport**: Cookie flags, Zod validation, and React state are outside this model; cover them with `pnpm check`, `pnpm test`, and `/verify-orrery`.
- **Unbounded actor counts**: M1 is bounded to 3 humans / 2 concurrent writers; M4 is bounded to 3 concurrent `PATCH`es.
- **M9 transaction boundary**: M9 is a bounded design model driven by source markers. It assumes atomic transitions; it cannot prove that token, account, membership, and grant writes use the same transaction or roll back together. The real-Postgres workspaces tests check both successful acceptance paths, verify database state after a stale-scope rejection, and prove that an owner's stale-scope offer is superseded by a fresh invitation that a recipient can accept.
- **M18 transfer boundaries**: M18 is a bounded design model driven by source markers. It explores authorization, authority/ownership changes, claim expiry and acceptance interleavings, but does not replay a real Postgres rollback, a concurrent second transfer, or invoke the HTTP adapters. The real-Postgres `transfers/transfers.test.ts` proves both two-party and single-party flows, claim and expired-claim boundaries in database time, stale authority/ownership refusals, source-key and offer cleanup, rebuilt Manage grants, receipt/grant events, and preserved issues and activity; the black-box `zz-transfer.spec.ts` proves the running image refuses the source key and that the destination owner sees Manage and the preserved history. M9 still models the narrower case of a project leaving an invited workspace before a pending offer is redeemed. Shared-to-shared transfer (#46) is deliberately out of this model: M18 uses a personal source where there are no source grants or membership events to preserve, though its acceptance core is the seam #46 will reuse.
- **M10 transaction boundary and concurrency**: M10 enumerates independent authority decisions in a bounded design model; it does not explore interleavings between two capability changes and a redemption, and it assumes the rejected `inviter_not_authorized` path rolls back the token and every earlier write in the transaction. Real-Postgres tests in `workspaces.test.ts` assert the invitation stays pending and no membership, account, or project grant commits. The live REST recipe in `verify-orrery/features/workspaces.md` covers the same ceilings through HTTP.
- **M11 transaction boundary and revocation races**: M11 enumerates independent key decisions in a bounded design model; it does not replay a real interleaving of an authentication transaction with a revocation or project-grant change, and it assumes the rejected paths write no key or event. The real-Postgres `agents.test.ts` proves the just-before/just-after expiry boundary in database time, the issuance ceiling, the lowered/removed grant ceiling, idempotent revocation, owner-revocation isolation, the audit rows, and that the database trigger rejects a cross-workspace key grant. The real-Postgres `workspaces.test.ts` proves that `removeMember` revokes the member's keys with one secret-free event, that re-invitation cannot revive the old credential while a new key works, and that `issueKey` and `removeMember` queue on the same ownership lock with no unrevoked key surviving. The black-box `zz-agents.spec.ts` proves the same HTTP outcomes against the running image, including human self-revocation.
- **M12 transport and attribution boundaries**: M12 is a bounded design model driven by source markers. It checks that the tool set and the two adapters call the one service gate and that the actor columns/constraints exist; it does not replay MCP frames or prove a particular HTTP status. The real-Postgres `agents.test.ts` proves agent attribution in stored rows and activity, Read-vs-Contribute denials, dynamic human-access capping, workspace/project scoping, and REST denial parity. The black-box `zz-mcp.spec.ts` drives the actual MCP protocol client against the built image for the same flows, including tool-list exposure, cross-workspace `list_projects`, out-of-scope, and revoked keys.
- **M13 query shape and payload contents**: M13 is a bounded design model driven by source markers in the history service, its thin REST adapter, and the shared contract. It checks which decisions exist and which fields a projection may select; it does not execute a SELECT or serialize a real response. The real-Postgres `history.test.ts` proves the scope matrix, non-enumeration status codes, all recorded event kinds through the view, and secret-free bodies. The black-box `zz-history.spec.ts` repeats the key denials against the running image.
- **M14 reporting boundaries**: M14 is a bounded design model driven by source markers and the partial indexes in `0019`; it checks that the mutation is in one `db.transaction` with `FOR UPDATE` re-reads but does not replay a real database interleaving, MCP frames, or a particular HTTP status. The real-Postgres `runs.test.ts` proves distinct runs under one key, resume preservation (including a concurrent pair), one clean history row for two simultaneous model changes, child linkage and scoped child run ids (self-loop, foreign agent, other workspace all refused), absent metadata staying null, key revocation, run-id scope, and human workspace scope. The black-box `zz-runs.spec.ts` drives two scripted MCP clients with one key against the built image for the same flows and verifies the persisted rows through REST. Claims and five-minute leases are deliberately out of scope (#36); M14 checks that no run tool advertises one.
- **M15 transaction and deployment boundaries**: M15 is a bounded design model driven by source markers. It checks the one-transaction `torn` outcome and the absence of bootstrap/ownership writes, but it does not replay a real rollback or execute the CLI inside a container. The real-Postgres `recovery.test.ts` proves the just-before/just-after expiry boundary in database time, single-use reuse, revocation of a second outstanding link by both redemption and local recovery, unverified no-mail, no live token after a failed send, session invalidation with agent keys untouched, that local recovery is administrator-only, and that it works with a broken sender without touching bootstrap or ownership. The black-box `recovery.spec.ts` drives the emailed flow through Mailpit, runs the local command in the container as the administrator with broken SMTP (proving the prior session is signed out), proves an ordinary account is refused, and checks that bootstrap and workspace ownership stay unchanged. Sensitivity of all 15 M15 guards was proven by mutating each guard in a throwaway copy of the sources and observing the shortest counterexample.
- **M16 rotation boundaries**: M16 is a bounded design model driven by source markers. It checks each rotation decision and the schema story that keeps the two keys independent (each key's own expiry, a `SET NULL` lineage FK rather than a cascade), but it does not replay a real revocation/expiry interleaving or execute the emailed reset inside a container. The real-Postgres `agents.test.ts` proves overlap, a fresh independent expiry, old-revoke isolation in both directions, preserved-grant capping and explicit-grant validation, refusals for revoked/expired/foreign/inaccessible sources, the secret-free `agent_key_rotated` row, and that both keys survive a real REST password reset; the new black-box `zz-key-rotation.spec.ts` repeats overlap, client switch, old-key revocation, password reset, and REST/MCP authentication against the built image. Sensitivity of all 13 M16 guards (and the shared `m15_agent_keys_untouched` guard) was proven by mutating each source guard in a throwaway copy and observing the shortest counterexample.
- **M17 transaction boundary and scheduler**: M17 is a bounded design model driven by source markers. It explores interleavings of claims, renewal, expiry, progress, fenced writes and downgrades, but it does not replay a real Postgres transaction rollback or execute a sweeper. The committed expiry that runs before a lease-taking transaction (so a refused renewal, progress report or stop still releases a lapsed lease), the `FOR UPDATE` serialization, the partial unique index and the DB-time lease boundaries are proved by the real-Postgres `work-sessions/sessions.test.ts`; the MCP client flows are proved by the black-box `zz-sessions.spec.ts`. The one-hour human-input deadline and Needs input lifecycle remain #37's scope; here `needs_input` is only a boolean filter on ready work.
- **M15 transaction and deployment boundaries**: M15 is a bounded design model driven by source markers. It checks the one-transaction `torn` outcome and the absence of bootstrap/ownership writes, but it does not replay a real rollback or execute the CLI inside a container. The real-Postgres `recovery.test.ts` proves the just-before/just-after expiry boundary in database time, single-use reuse, revocation of a second outstanding link by both redemption and local recovery, unverified no-mail, no live token after a failed send, session invalidation with agent keys untouched, that local recovery is administrator-only, and that it works with a broken sender without touching bootstrap or ownership. The black-box `recovery.spec.ts` drives the emailed flow through Mailpit, runs the local command in the container as the administrator with broken SMTP (proving the prior session is signed out), proves an ordinary account is refused, and checks that bootstrap and workspace ownership stay unchanged. ## Interpreting Failures & Maintaining the Skill

- **Real bug vs. modeling error:** Open the files listed in the failing check's output. If a lock, guard, or SQL predicate was removed or reordered, the counterexample trace shows a real bug — fix the product code and add a real-Postgres regression test. If the product code was intentionally refactored to enforce the same invariant via a *different* mechanism (e.g., a new DB constraint or different helper name) so `extract_code_facts()` no longer recognizes it, update `extract_code_facts()` and the transition model in `scripts/verify.py` to match the new mechanism, prove it still fails when the mechanism is broken, and advance the sync commit above.
- **Sensitivity proof:** each `attempts` tuple carries the outcome *when its guard is missing*, so a deleted source guard makes the shortest counterexample name the exact request. To prove a model is sensitive without editing product code, import `scripts/verify.py`, copy `extract_code_facts()`, flip one fact to `False`, and assert the check becomes `violated`; restore by rerunning the normal command. M13 was proven sensitive to `m13_workspace_404`, `m13_admin_only`, `m13_no_secret`, `m13_session_only`, and `m13_manage_access` when it was added. M16 was proven sensitive to all 13 of its extracted guards (lock, source ownership, revoked/expired/workspace refusals, same target, one-time secret, independent expiry, grant capping, non-cascading lineage FK, secret-free event, history surface, and 400 Problem) plus the shared password-reset guard.
